我的总体判断是：项目已经积累了不少执行与恢复能力，但研究证据明显落后于工程扩张。当前实现还不能支持“校准了观察和推理的增量价值”，主要支持的是“预测部分动作失败，再用启发式选择干预”。更紧迫的是，代码中的权限边界尚未兑现“agent 不能放行自己”这个承诺。接下来应暂停增加模型角色，优先修安全边界、建立真实反事实数据、补齐公平对照。

审阅依据是 gui-gate 的 [`b4ddb067` 提交](https://github.com/cszf1/gui-gate/tree/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa)；gui-pi-desktop 当前主分支只有设计文档，因此桌面部分属于设计审阅。以下代码问题来自静态检查，未运行攻击复现；53.7% 按你提供的结果快照讨论。

**1. 研究与工程：先把“失败预测”与“干预收益”分开**

**问题在哪 →** 你现在混合了三个不同问题：

- 动作是否能正常执行。
- 多观察、多推理是否能改善结果。
- 动作是否被授权、是否允许执行。

它们需要不同标签和验证方法。`deny/handoff/ask_human` 不是普通的效率选项，不能和截图、等待放在同一个收益排序里解释。七个角色、技能、自愈、批量执行同时开启后，任务成功率提升也无法归因给价值预测器。

另外，“联合估计 direct/观察/推理/等待”是否构成文献空白，目前应视为**待验证的研究假设**。除了 GUI agent 工作，还需要对照元推理、信息价值和预算下的策略选择研究。

**建议怎么改 →** 把主研究先收窄到：**安全允许的状态中，额外观察或推理是否值得付出成本。**

定义清楚：

\[
\Delta_o(x)=P(Y_o=1\mid x,\pi,B)-P(Y_{\mathrm{direct}}=1\mid x,\pi,B)
\]

这里 \(x\) 是干预前可见信息，\(\pi\) 是固定的后续控制策略，\(B\) 是包含干预开销的剩余预算，\(Y\) 是明确的成功标准。这个增量依赖主模型、提示词和预算，不是 GUI 状态天然具有的属性。

先固定以下处理协议：

| 处理 | 实验中究竟做什么 |
|---|---|
| direct | 执行已生成的候选动作 |
| look_light | 获取新树，让同一个控制器重新选择动作 |
| look_full | 获取新树与截图，再重新选择动作 |
| extra_reason | 不提供新观察，增加固定推理预算，允许改候选动作 |
| matched_wait | 等待与对应观察／推理匹配的时长，不提供新信息，再执行原候选 |

`extra_reason` 是重新生成候选，**不产生安全授权**；独立审核仍照常执行。当前 `review` 如果只是允许／拒绝原动作，就不能直接当成“多想一下”的等价实现。

反事实采集建议从小而严格的实验开始：

1. 在候选动作生成之后，冻结环境、候选动作、完整模型上下文、门的缓存与历史、剩余预算。
2. 从这一检查点恢复出所有分支，随机化执行顺序，每个分支重复运行。
3. 同一检查点必须恢复文件、焦点、剪贴板、窗口、应用状态和相关计时状态。**截图相同不代表状态相同。**
4. 先用可序列化的 GTK／本地网页夹具做严格分支，再用 OSWorld 做完整任务验证。当前 native setup/reset 不是任意中间状态快照。
5. 可先做约 100–200 个检查点、五种处理、每种三次重复，估计方差后再决定扩容；这只是试点规模，不保证统计功效。

标签至少分三层：驱动是否报错、是否完成预先定义的局部子目标、剩余预算内任务是否成功。局部标签可以便宜，但不能用“没报错”替代“对任务有帮助”。

**怎么验证改对了 →**

- 按**任务族**划分训练、校准、测试；同一任务的所有状态、布局变体、分支和重复运行不得跨集合。跨运行留出不自动等于未见任务。
- 单独做未见布局测试；有余力再做未见应用测试。
- 对每个选项按预测增量分箱，比较“箱内平均预测增量”和“配对分支的实际平均成功率差”，允许负增量，并给任务层面的置信区间。
- 同时报告各选项概率的 Brier、NLL、可靠性图。AUC 只能说明排序，不能证明增量校准。
- 最终检验冻结测试集上的**预算—成功率曲线**：是否优于固定策略、置信度阈值，以及相同干预次数的随机策略。

消融不用把全部开关做笛卡尔积。主链足够：

> 固定安全与工程底座 → 仅启发式 → P(direct)＋固定增益 → 学习各选项收益 → 加增量校准。

自动观察、自愈、上下文压缩、七角色包再分别做成组消融。

**2. 预测器：逻辑回归可以保留，伪反事实应当替换**

**问题在哪 →** 主要错误不是“只有三十个特征”，而是把相关性模型当成了干预模型。

[`decide.rs`](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/src/decide.rs#L62) 中：

- wait 直接清除 loading、popup 特征，但等待并不保证它们消失。
- review 清除重名、重复、先前失败特征，但审核并没有改变这些事实。
- `p_direct(after(...)).max(p)` 再加非负残差，强制干预不会降低成功率。真实情况下，多想会改错，等待会错失时机，新观察也可能造成误导。

[`tools.rs`](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/src/tools.rs#L97) 的训练数据主要来自已经执行且最终 decision 为 direct 的动作，标签主要是无报错、无 stale error、无某类重复。它既有标签偏差，也缺少被门拦下状态的 direct 结果。

此外，[v3 权重文件](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/weights/osworld-v3.json) 中一组测试结果的 ECE 在 Platt 后由 0.0307 变成 0.0324，Brier 也略差。差异很小，但足以说明：**用了校准算法，不等于已经证明校准改善。**

**建议怎么改 →**

第一版仍可用正则逻辑回归，但输入加入处理类别及其与状态特征的交互，直接学习：

\[
q_o(x)=P(Y=1\mid do(o),x),\qquad \Delta_o=q_o-q_{\mathrm{direct}}
\]

用随机分支数据训练，允许负增量；再与每个处理一个模型、小型树模型比较。没有必要马上上复杂因果森林。

历史日志可以辅助预训练，但不要指望 CATE 或 doubly robust 方法自动修复所有问题：未记录的混杂因素、从未尝试过的处理，无法靠换估计器补出来。

还有三个具体修改：

- **成本实测。** 分别估计延迟、模型费用和人的主动操作时间。固定 7／9／45 秒只能是初始先验。
- **check 按信息价值处理。** 它的收益来自“检查结果改变后续选择”，不是检查本身增加 3% 成功率。当前“算完最优选项，再强制先 check”也不是所写期望代价公式的最优解，应单独消融。
- **给增量区间。** 按任务重采样训练一组模型，估计净收益的不确定性；证据不足或超出训练覆盖时，回退到固定策略。不要把模型不确定性一律转成人工弹窗。

需要特别收窄一句产品目标：门在主模型生成动作之后才工作，**省不掉刚刚已经发生的那次推理**。若要调度下一轮截图或额外思考，Pi 必须在相应调用前向同一个 Rust 门取得策略决定；否则主张应限定为减少追加观察、返工和恢复开销。

**怎么验证改对了 →** 在完全相同的数据划分和工程底座上比较旧方法与新方法，检查负增量状态能否识别、增量可靠性是否改善，以及策略收益是否改善。另需冻结训练先验：当前训练器使用已经训练过的 `prior_weights()` 作正则中心，若拿它重做包含旧训练数据的留出实验，可能泄漏测试信息；这不证明历史结果已泄漏，但复现实验必须消除这个风险。

**3. 安全：有具体边界漏洞，不能只继续补关键词**

**问题在哪 →** 以下是已经核实的代码路径问题。

| 问题 | 具体后果 |
|---|---|
| `gate_config` 只从默认工具列表隐藏，分发器仍接受调用并修改 `policy/risk_confirm` | 隐藏工具没有形成权限边界 |
| `policy_decision` 在安全硬规则之前返回 | direct/light/full 可绕过后续安全判断 |
| 部分授权仍接受 agent 提交的 `gate_task`；对象匹配依赖关键词、文件名 | 模型转述可能被升级为危险动作授权 |
| `session_owned` 用“mtime 晚于会话开始”判断 | 用户旧文件被修改后，可能错误获得删除／移动豁免 |
| 部分 heal、重绑定、恢复点击直接派发动作 | 实际执行对象变化后，没有统一重新验证授权 |

前两项见 [`server.rs` 的分发和决策顺序](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/src/server.rs#L1726)；授权见 [`authz.rs`](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/src/authz.rs#L142)，mtime 判断见 [`sidefx.rs`](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/src/sidefx.rs#L360)。

还有一个架构问题：把 bash 入口换成 `run_command`，再加正则检查，不能证明任意脚本安全。若模型能以同一用户权限运行任意代码，它可能接触门的配置、驱动入口、审批 IPC 或凭证。拆成多步、换解释器、从 GUI 终端输入，都超出了关键词规则能可靠覆盖的范围。

**建议怎么改 →**

先建立三个不可绕过的边界：

1. **模型不可修改安全配置。** 生产协议删除或拒绝该管理入口；实验策略由可信启动参数指定。所有策略先经过相同安全层。
2. **授权只能来自可信用户通道。** 壳直接提交原话与版本，agent 提交的任务描述仅作为上下文。授权绑定操作、资源、接收方、范围、金额／内容及有效期。
3. **只有一个最终动作派发入口。** 重定位、heal、后台输入、批量子步骤、恢复重试都必须通过它，检查最终动作及当前前置条件。对象发生实质变化，旧批准失效。

独立外部审核模型继续保留，但它不能凭空授予用户权限，也不能覆盖明确拒绝。独立调用也不意味着错误相互独立；界面树里的提示注入可能同时误导两个模型。

“同一效果已被拒”不要继续使用文件 basename 或理由字符串。建议保存结构化效果：

```text
操作 + 资源身份 + 目标位置/接收方 + 内容或金额摘要 + 操作范围
```

资源身份按类型处理：文件用路径与文件身份、站点对象用站点＋账户＋对象 ID；覆盖尚不存在的目标要绑定父目录和目标名。对目录删除、批量发送还需要集合包含关系，单个哈希相等不够。

**拒绝记录与批准凭证要分开：**

- 拒绝记录覆盖稳定的效果范围，换措辞、换工具不应绕过。
- 一次批准精确绑定动作、目标版本、请求、会话和有效期。
- 可信用户的新指令可以改变授权；模型自己重写任务不可以。

MRTR 的方向正确，但顶层 `inputResponses` 还不够。必须一次消费、防重放、重启失效，并在批准期间冻结自动输入，避免 agent 操作自己的批准弹窗。当前把 `gate_confirm` 交给模型再收回的旧路径应彻底移除。

若仍允许不受限的同用户任意代码，就应明确产品只提供合作型 agent 的误操作防护。要声称能抵抗恶意模型绕过，需要 OS 权限隔离；可以由 Rust 管理受限进程，不要求增加 sidecar。

**怎么验证改对了 →** 增加“绕过也失败”的测试，而不只是“弹窗能出现”：直接调用隐藏工具、伪造用户原话、同名不同路径、旧文件修改后删除、批准后换窗口、重绑定后目标变危险、跨工具实现同一被拒效果、重复／串线审批响应。真门＋假驱动测试这些确定性性质，真桌面测试状态竞争；不能只靠真模型偶然没有绕过。

**4. 问人体验：四种语义够了，重点是问什么和何时问**

**问题在哪 →** 四种弹窗并不多，但如果都表现为“卡住后弹一下”，仍会很打扰。连续失败次数不能独自决定求助价值；有些偏好应在第一步澄清，有些失败再试一次就能恢复。

`approve`、`answer`、`takeover`、`help` 也不能统一转成 allow。例如用户回答了一个问题，不代表批准发送；用户接管完成，不代表应该重新执行原动作。

**建议怎么改 →**

界面可以共用一个组件，底层保留四种严格的结果类型：

- 批准：显示门确认的具体对象、范围和后果。
- 澄清：说明不同答案会怎样改变后续操作，尽量给少量选项。
- 接管：暂停自动输入，说明需要人完成的最小步骤。
- 求助：简述已尝试的方法，让人选择代做或提供提示。

问人价值通常最高的情况是：只有用户知道的信息会改变整个后续路径；不可逆动作缺少明确授权；继续观察和推理已经无法补足所需信息。

安全上必须询问的步骤不参加成本交易。可选澄清和求助才比较“预计任务收益”和“中断成本”。

保留“超时＝拒绝”，但记录原因。超时拒绝本次动作，不等于用户明确永久反对该效果，也不应训练成“用户不愿帮助”。不能因此立即循环再问。

**怎么验证改对了 →** 真实用户试点至少记录：

- 每任务询问次数、重复问题比例。
- 人的主动操作秒数、等待秒数、接管步骤数。
- 取消／超时率、错误批准率。
- 成功率、总完成时间、简短的打扰评分。

用任务配对或平衡顺序比较阈值询问和价值询问。模拟人适合调协议，`--human deny` 适合测无人运行；两者都不能证明人的负担下降。

**5. agent 侧：先修执行结果契约，再优化上下文**

**问题在哪 →** 有一处应立即改掉：桌面设计和门提示词都说“`[gate]` 表示没有执行”，但代码也用它返回执行后的观察——[`server.rs:2394`](https://github.com/cszf1/gui-gate/blob/b4ddb067c96f7e07287fd3fe6ca9c173649b46fa/src/server.rs#L2394)。这会诱发重复点击、重复输入甚至重复提交。

上下文方面，门已经生成树 diff，扩展又准备做 diff 和删除旧观察。两个模块分别压缩，容易把差分依赖的基底删掉。“只留最新一张截图”也会伤害跨窗口抄数据、视觉修改前后比较等任务。

**建议怎么改 →**

先返回结构化执行状态，例如：

```text
status: executed | blocked | input_required | unknown
action_id, completed_steps, observation_id, next_action
```

`unknown` 用于“可能执行了，但结果不确定”。此时先核验状态，禁止盲目重放。批量结果必须明确已经完成哪些步骤。

上下文只设一个差分负责人：

- 门提供完整树或带 `base_snapshot_id` 的结构化差分。
- 客户端确定性重建当前树，再决定给模型展示什么。
- 压缩后仍须提供有效基底或重新生成的当前树。
- 删除节点、索引重排、窗口重建必须显式处理，不能只发送新增行。

保留“每窗口当前状态”，另存少量任务事实：值、来源、时间、验证状态。用户原话、授权、人的回答由程序保存原文与来源，不能靠压缩模型重新概括。

截图改成“最新图＋少量任务必需的固定证据图”，原尺寸 JPEG q60 不变；其余图片保留在会话存储，需要时再取。

计划只设一份权威状态。每轮机械附计划提醒可能固化错误路线，优先在里程碑变化、压缩后或偏航时提醒。平台／应用技能按需加载，删掉系统提示、门简报、skills 中重复的说明。

**怎么验证改对了 →** 先验证差分重建等于完整树，再比较完整上下文、当前压缩方案、新方案在跨窗口、视觉编辑和长任务上的成功率。报告旧 token 错误、重复动作、任务事实丢失、token 和耗时。仅证明上下文变短，不足以证明改进。

**6. 评测：必须补基线，但不能直接拿当前 direct 开关作消融**

**问题在哪 →** 137/255＝53.7% 是有效运行上的描述性结果。普通二项 Wilson 95% 区间约为 **47.6%–59.7%**，尚未考虑任务相关性和有效样本选择问题。

更关键的是，当前 direct 同时改变安全检查、自动观察、截图默认行为和部分自愈。它与 gate 的差异远不止价值预测器，所以即使补跑，也不能直接证明增量估计有效。

**建议怎么改 →** 分开做两个实验：

- **研究实验：** 同一个 agent、同一个工程底座，只替换干预策略。
- **产品实验：** 完整新桌面 agent 对旧系统，衡量整体效果。

研究实验建议包含：

| 策略 | 用途 |
|---|---|
| direct | 不由价值模块要求额外干预，其余机制固定 |
| 每步观察 | 固定树观察；截图版另列 |
| 固定额外推理 | 检查自适应推理是否优于固定投入 |
| P(direct) 阈值 | 检查增量估计是否优于失败概率 |
| 仅启发式 | 检查学习模型的贡献 |
| 学习增量，校准前／后 | 检查校准的决策价值 |
| 等时等待、同干预率随机 | 区分加载等待效应与状态选择能力 |

不必立即把所有条件在 361 题上跑很多遍。先在开发集排除明显无效方案，冻结方案后再进入未参与调参的测试集。不能看测试成绩不断调整规则。

至少三次独立重复作为起点，按任务配对、交错运行新旧系统，报告任务层面的配对置信区间。若 API 没有真正传入采样种子，就称“独立重复运行”；日志名写 seed 不代表控制了随机性。

另外必须做到：

- 预先冻结任务名单、排除原因和重试规则，同时报告全体预定任务与有效任务结果。
- API 错误不能因为某策略调用更多而被随意删除；这也是系统可靠性的一部分。
- 统计所有角色、审核模型、实际 GUI 动作、截图、费用和总耗时。100 个 Pi turns 不等于 100 个环境动作。
- 耗时分析包含失败和超时；不要只在成功样本上比较速度。
- 经验记忆、校准器、手工规则都不能使用测试答案。
- 增加未参与调参的新布局／新任务集，避免 OSWorld 成为不断修题的开发集。

**怎么验证改对了 →** 最有说服力的结论是：“在固定预算下成功率提高”，或“成功率下降不超过预先约定界限时，时间明显减少”。“成功率差异不显著”不等于证明没有下降。

当前 native 环境、应用版本和预算定义与官方不同，应报告为**基于 OSWorld 任务与评估器的自定义环境结果**，不直接与官方榜单数字对齐。

**7. 桌面产品化：四层可以接受，职责重复和权限继承才是负担**

**问题在哪 →** Tauri＋Pi＋门＋驱动并没有明显多到需要重写。真正复杂的是：谁管理计划、谁压缩、谁重试、谁拥有凭证，以及某一层崩溃后其他层会不会继续操作。

“密钥只通过环境变量传递”也不等于隔离。当前命令子进程默认继承环境，部分角色探测还允许 `env/printenv`；按照桌面设计注入密钥后，存在具体泄漏路径。

**建议怎么改 →**

保留四层，收紧职责：

- Tauri：可信用户输入、设置、密钥、进程生命周期。
- Pi：任务规划、模型上下文、应用技能。
- gui-gate：安全、价值选择、受控执行与短程恢复。
- 驱动：观察与输入。

七个角色中，planner、search、compact 等不必都留在门里。可以先关闭、后续迁移职责，无须改变 Rust MCP server 和不加 sidecar 的约束。设置页将它们放进高级设置；二分类审核接口也未必能直接兼任 planner 或 compact。

每个子进程显式构造环境白名单：Pi、门各得所需凭证，驱动、命令及辅助进程不得继承模型密钥或审批 token。钥匙串不可用时拒绝明文回退，这条保留。

平台上优先处理这些具体问题：

| 平台 | 重点 |
|---|---|
| Linux | 明示 X11 支持范围；验证 AT-SPI、DBus、Secret Service、WebKit/glibc 依赖；Wayland 单列 |
| Windows | UIA 缺失、权限完整性等级、UAC 安全桌面、DPI／多屏、RDP 断开；命令接口不能直接套 bash 规则 |
| macOS | 辅助功能与屏幕录制分别授权；权限撤销和重启；签名身份稳定；Retina 坐标换算 |

不缩小截图只保证图片像素没变，**不保证驱动输入坐标与截图坐标天然一致**，仍需明确窗口原点、缩放和显示器。

发布固定整套版本与提交哈希，保留驱动签名，更新可回滚。优先测试停止、崩溃、断连和升级中断，而非先把三个平台的设置页做完整。“零残留”也应有明确范围，不能误删原来已安装的驱动或用户数据。

**怎么验证改对了 →** 在干净机器上覆盖安装、升级、撤销权限、杀掉任意一层、关闭壳、重复响应、驱动重启。断言停止后不再发新动作，旧观察与旧审批失效，结果未知的动作不会自动重放。用假密钥检测命令环境、角色输出和日志中的泄漏。

六条既定规则我不建议推翻，但两项表述要降格：

- 独立审核模型是必要的防线之一，不是不可绕过的充分条件。
- JPEG q60 可以保留；现有实验的“不显著”不能写成已证明与 PNG 等效，三倍首 token 加速也应限定到已测试的模型和接口。

**8. 如果只能再做三件事**

**问题在哪 →** 当前范围同时包含研究方法、通用 agent、安全运行时、跨平台桌面产品。对 SRTP 来说，这会让每一部分都有功能，却没有一部分得到充分验证。

**建议怎么改 →** 三件事依次是：修不可绕过的执行与授权边界；建立严格的反事实数据；完成冻结条件下的比较实验。它们分别决定系统是否可信、研究对象是否真实、论文结论是否成立。

**怎么验证改对了 →** 每件事都以可检查的交付物结束，而不是以版本号、代码行数或新增开关结束。桌面版先作为 Linux 实验入口，Windows/macOS 完整产品化和新增角色后置。

**我会先做什么**

| 顺序 | 具体交付物 | 完成标准 |
