1. 研究与工程：先把优化目标和研究对象分清

问题在哪

当前公式

\[
E[cost(o)]=\lambda c_o+(1-P_o)C_{\rm fail}
\]

本身可以作为近似，但它隐藏了三个未经验证的假设：

- 所有选项的 \(P_o\) 预测的是同一件事。
- 一次失败的后果可以压成一个 \(C_{\rm fail}\)。
- 观察、推理或等待之后，剩余任务的难度基本不变。

实际并不成立。direct 执行原动作；look_full 可能让模型换动作；ask_help 甚至换了执行者。把这些结果统一标成“下一次驱动没报错”，比较的就不是任务价值。

另外，deny、授权、密码接管、必要的安全检查，不应和可选观察一起竞争期望收益。你现在坚持安全先行是对的，研究实验也必须保留这条边界。

建议怎么改

明确两层目标。

第一层是产品目标：在固定预算和安全约束下完成任务。令 \(h\) 表示当前历史、候选动作及观察，\(b\) 表示剩余预算，固定后续 agent 策略为 \(\pi\)，定义：

\[
Q^\pi(h,b,o)
=
E\!\left[
L(1-Y_o^\pi)
+\lambda T_o^\pi
+\gamma H_o^\pi
+\eta N_o^\pi
\mid h,b,do(o)
\right]
\]

其中：

量	含义	来源

\(Y_o^\pi\)	采取选项后，在预算内最终是否成功	任务评测器
\(T_o^\pi\)	从当前决策到结束的剩余时间	计时，包括失败和超时
\(H_o^\pi\)	人的主动操作时间	客户端交互记录；目前数据不足
\(N_o^\pi\)	可选介入次数	决策日志
\(L,\lambda,\gamma\)	成功、时间、人力之间的取舍	产品偏好或预注册约束，不是日志能自动决定的
\(\eta\)	控制介入频率的预算价格	开发集或预算控制器


只能在安全规则允许的集合中选择：

\[
o^*=\arg\min_{o\in\mathcal A_{\rm safe}(h)}Q^\pi(h,b,o)
\]

第二层是现阶段能做的小模型：预测某个介入相对 direct 的局部净收益：

\[
G_o(h)
=
C_{\rm recover}(h)\,\Delta p_o(h)
-\lambda\Delta t_o(h)
-\gamma\Delta H_o(h)
-\eta\,1[o\ne direct]
\]

这里的 \(\Delta t_o\) 应明确为额外前置耗时；否则若已经包含失败恢复时间，再加 \(C_{\rm recover}\Delta p\) 会重复计算收益。

我建议暂时保留这种局部模型，加一个明确的“连续失败—换策略—求助—停止”状态机。现在直接上完整强化学习，数据量和标签质量都支撑不了。

标签分三层记录，不能互相冒充：

1. 执行结果：驱动是否送达、是否报错、结果是否未知。
2. 局部进展：目标控件、文件或应用状态是否达到预期后置条件。
3. 任务结果：预算内最终成功，以及剩余耗时。

尤其不要把同一个任务成败复制到该任务所有动作后，就称为“动作价值标签”：这会让长轨迹被重复加权，也混入后续策略的影响。

怎么验证

论文的核心应当是：在同一可恢复状态下，分支运行不同选项，固定后续策略及预算，检验预测增量：

\[
\hat\tau_o(h)
\approx E[Y_o-Y_{\rm direct}\mid h]
\]

除了各选项的 Brier、NLL、可靠性图，还应画增量校准图：按预测 \(\hat\tau_o\) 分箱，比较箱内预测均值与配对分支的实际平均差。允许负增益。

最后用完整在线任务验证策略收益。风险 AUC 更高、抓到更多历史失败，都不能替代这一项。

2. 预测器：目前最大的障碍是数据定义，不是模型表达能力

问题在哪

新版确实已经增加 treatment 模型、覆盖检查、负增益和区间，但还有几个根本问题。

① 日志仍混入处理后的特征。

check、wait、heal 后会重新计算 f，最终动作事件记录的就是这个 f；wait 后还直接把 loading_cue、last_popup 清零。server.rs

训练端继续读取事件中的 features。排除 check_pass/check_fail 并不能消除观察年龄、token 状态、窗口状态等已经发生的变化。valuetrain.rs

因此，部分样本估计的是“处理之后这个状态容易成功吗”，不是“处理之前选择这个选项有用吗”。

② hand-back 的标签归属过于宽松。

训练器把 180 秒内待标注的多个介入，都用下一次执行动作的结果填上；没有要求是同一候选动作、同一效果或同一续接决策。代码

这可以作为粗糙的流程统计，不能直接解释成某个处理的成功概率。

③ IPW 没有解决覆盖和混杂。

新版训练数据中：

选项	训练行数	IPW ESS	拟合 propensity 达阈值的状态比例

direct	3931	3894	100%
wait	184	110	29.4%
look_full	55	42.9	4.4%
review	31	30.1	1.4%
heal	26	24.3	3.0%
look_light	18	18	0%
check	12	12	0.3%


来源：新版离线报告。

这说明多数处理没有足够证据支持上线。但也不能反过来说“direct/wait 已经可识别”：softmax 预测出非零概率，不代表原来的确定性策略真的会在该状态选择另一条路径。

运行时 covered(o) 还是选项级的全局门槛，不检查当前状态是否同时支持 direct 和该选项。value.rs

④ 区间仍偏理想化。

bootstrap 重采样时复用了原训练集拟合的 propensity 权重，没有重新估计；拟合迭代数也缩短了。训练代码

目前 30 个模型副本适合检查管线，不适合把区间端点当成稳定的决策依据。

建议怎么改

先补数据契约，再考虑模型：

- 保存不可变的 x_pre，另存 x_post。
- 记录 decision_id、原候选动作、效果标识、完整处理链、续接决策 ID、处理起止时间。
- 区分“提议了什么”“实际做了什么”“模型换成了什么”。
- waited=1 与 loading_cue=0 分开。等过了不代表加载真的完成。
- 历史数据无法恢复处理前状态的样本，排除出因果估计，保留作描述统计。

模型先用共享主干加处理交互的 logistic，或有收缩的分处理模型。现有样本不适合给每个选项单独训练一个高自由度模型。

有可靠覆盖时，可以用交叉拟合的 doubly robust 估计，例如：

\[
\phi_o=
\hat m_o(X)-\hat m_d(X)
+\frac{1[A=o]}{\hat e_o(X)}(Y-\hat m_o(X))
-\frac{1[A=d]}{\hat e_d(X)}(Y-\hat m_d(X))
\]

但它依然依赖处理定义一致、处理前协变量充分、存在重叠。DR 不是补出缺失反事实的魔法。

选择选项时，建议比较各选项净收益的保守下界，而不是先选点估计最大的选项，再只检查它。未覆盖时明确返回“没有估计依据”，不要悄悄退回手工增益后仍称为 learned policy。

check 的信息价值还没有真正估出来。

正确结构是：

\[
VOI_{\rm check}
=
\min_a Q(h,a)
-
\left[
c_{\rm check}
+E_z\min_a Q(h,z,a)
\right]
\]

新版没有 probe 模型时，仍通过翻转特征并倒推 \(P(pass)\) 来计算；treatment 分支选择 check 时也只看点估计正不正，没有与其他选项相同的区间约束。实现、选择逻辑

在有探测结果与后续收益数据前，建议把它叫“便宜验证启发式”。另外，若 check 会重绑参数，就同时包含修复效果，不能全部算作纯信息价值。

成本与预算也要分清。

当前 C_fail 仍是 2 × turn_cost + side_cost 乘严重度和连续失败因子，是先验。decide.rs

可以从日志估计失败后的恢复时间，但这只是相关性代理；任务失败的产品损失 \(L\) 仍需人为指定。5–10% 介入预算最好由独立的 \(\eta\) 控制，\(\lambda\) 控制时间取舍，因为一次 check 和一次 look_full 的成本相差近百倍。

怎么验证

- 先人工复核 click/scroll 的失败标签。新版数据中 scroll 的 35 个失败有 23 个来自重复判定，重复滚动不一定失败。
- 对新增特征按组消融：可视区、enabled、遮挡、坐标系、应用类型，各报配对 AUC/Brier 增量区间。
- 当前新增特征整体 AUC 增量是 −0.0034，95% CI [−0.0179, +0.0115]，没有可靠收益证据。
- 历史日志缺少相关视觉和几何信息，不能从这些数据补算“遮挡特征提升多少”。应从新日志开始采集，并保留缺失标记。
- 坐标偏移要记录坐标系、窗口原点、DPI 和实际偏差，不能把 LibreOffice 的约 27 px 写成通用补丁。

3. 安全边界：已有修复应认可，但还不能称为完整闭环

问题在哪

新版已经有实现及回归用例覆盖：冲突答案按拒绝处理、任务变更后旧审批失效、reset 不解除问人冻结、读工具夹带写参数被拒、旧确认码路径封闭，以及审批凭证与拒绝记录分离。这些不应继续列为“尚未修复”。

我仍建议优先处理以下问题：

当前问题	代码证据与判断	建议的验证用例

后台输入回退没有重新经过最终检查	首次发送经过检查；后台不可用时第二次直接调用 tool_raw。代码	首次明确未送达后改变目标或审批前提；第二次派发必须重新校验
unknown 只是暂时挡住	unknown_sigs.remove() 在重新观察前就移除；无模型目标路径甚至读取窗口失败后，也已清掉记录。代码	动作实际已执行、返回丢失；随后读窗口失败，再发相同动作，不能重复执行
审批绑定不等于实际效果绑定	GUI 效果通常是控件标签、窗口和点击参数；payload 没有收件人、金额、正文等表单状态。代码	批准同一个 Send 按钮后，改变收件人或正文；旧批准必须失效
审核失败仍可能退回 direct	价值模型选择的 review 在审核无响应时，会选其他分数最好的选项，可能是 direct。代码	假审核服务超时，分别检查有真人、无人两种行为


前三项的代码路径可以确认；具体危险效果能否在真实桌面上触发，本轮没有动态验证。第四项主要是与你“审核出错有人问人、无人拒绝”的硬约束不一致，不能直接说成风险审核被绕过，因为风险路径另有保护。

建议怎么改

1. 每一次实际发送都经过同一个检查入口。 包括重试、后台转前台、焦点修复、批量内部动作。只有驱动明确保证“未送达”时，才允许自动重试。
2. 把 unknown 做成未解决状态账本。 对发送、删除、支付等非幂等效果，读过窗口不能自动解除；需要确认未执行、明确的幂等机制，或真人核实。
3. 审批前后验证业务前提。 窗口 ID 没变，不代表发送对象和内容没变。尽可能绑定资源、收件人、范围、内容摘要及对象版本；无法读取关键状态时，承认不可验证。
4. 拒绝键与批准键继续分开。 拒绝可按资源范围覆盖；批准应严格、一次性、短时有效。现在仍存在 basename 回退和“同应用同标签”的粗粒度匹配，要明确这是保守近似。
5. 效果 payload 当前使用 FNV-1a 64 位。既然参与审批等价判断，建议改用密码学摘要；这不是声称现有数据里发生了碰撞攻击。effect.rs

另有一处文档概念错误：requestState 有签名，只能证明它是门发出的状态，不能证明填写的 allow 来自真人。经手合法状态和答案的扩展属于可信计算基的一部分；不能因为有 HMAC 就称它“半可信且无法代答”。

桌面新版把威胁模型明确为“合作但会犯错的 agent”，这是合理收缩。任意命令仍以同一用户运行时，关键词规则和独立审核不能构成恶意代码沙箱；换解释器、分步构造、调用 GUI 自动化等路径无法靠继续补词表彻底解决。

怎么验证

攻击测试要断言驱动实际收到多少次什么动作，不能只检查回复文本是否包含 deny。再加状态变化测试：同窗口内容变化、跨工具同效果、批准后超时、任务更新、问人期间后台命令继续运行。

安全测试与成功率测试分开报告；有限攻击集全通过，也不应写成“无绕过”。

4. 真人交接：四种语义够用，重点是状态和计量

问题在哪

四种类型没有明显冗余，批准、澄清、代做、求助确实不同。新版 did_it 与 another_way 分开也正确。

但人的负担统计仍不可信：note_burden 把有回答请求的全部等待时间，同时记为 active_s。代码

另外，现有评测用 human=deny。其中约 44 秒的 ask_human 间隔不是人的响应时间，不能用来验证“问人成本 45 秒”。

文档也承认：MRTR 无重试过期的请求没有进入 unanswered，同一效果仍可能再次弹窗。

建议怎么改

- 批准：显示具体对象、范围、后果；它只批准这个效果。
- 澄清：问一个会改变后续选择的问题，给少量有实际差别的选项。
- 接管：给最少操作步骤，完成后重读受影响状态，禁止自动重放原动作。
- 求助：展示已经尝试过什么，让用户选择提示或代做。

安全必需的批准不能因为“问人收益低”而跳过。可选澄清和求助才做价值判断：用户是否掌握模型无法获得的信息、继续尝试是否仍有进展、剩余预算是否足够。

每个请求保存统一记录：请求 ID、任务版本、效果、问人类型、截止时间和唯一终态。过期、断连、迟到答复、reset 都走同一个收尾过程，避免漏计、重复计和再次询问。

怎么验证

分别报告：

- 每任务打断次数、重复询问率、无回答率；
- 从弹窗到回答的等待时间；
- 有交互证据的主动操作时间；
- 接管完成率、交还后重复动作率；
- 用户主观打扰程度。

主动时间测不到就记缺失或上界，不要用等待时间代替。交还测试应包含用户切换窗口、修改文件和改变当前焦点，不能只测试按“完成”按钮。

5. 观察与上下文：新版方向正确，但“原样保留事实”还没有做到

问题在哪

新版桌面扩展已经实现按 base_snapshot_id 保留 diff 链、固定证据图、图片召回，旧版“全局只留最新截图”的问题不能再照搬。

现在有三个具体缺口。

第一，任务原话会被截断，而且只保存第一次。

TaskFacts.setRequest() 限制 4000 字符，已有 request 时直接拒绝更新；压缩回退还只取首条用户消息的前 2000 字符。facts.ts、压缩逻辑

因此，这份持久记录不能保证后续用户更正跨压缩保留。Rust 任务文件的授权通道是另一回事；这里首先影响任务理解。

第二，确定性压缩可能丢失过程信息。

目前主要保留 facts、计划、证据图和最后窗口。若模型没有主动 note_fact，已经试过的失败方法、未完成的子目标、临时操作约束可能消失。

第三，gate_next_step 用虚构点击调用动作模型。

它构造一个无实际目标的 token click，再交给 choose()。代码

这是另一个分布。针对具体动作校准的预测器，不能直接证明“下一轮要不要观察”也校准。

建议怎么改

- 保存带版本和来源的用户消息序列；展示可截短，权威记录不截短。
- 自动记录最近的失败方法、未验证假设、未完成操作，避免全靠模型主动记笔记。
- facts 中继续区分模型备注与工具证据；check_done 模型说没有缺口，不等于环境已证明成功。
- gate_next_step 暂时用独立规则或独立状态模型，不复用虚构动作概率。
- 自动观察与下一轮前观察共用新鲜度判断，避免刚附完树又读一遍。
- diff 链太长时重新生成完整锚点；基底缺失时，客户端主动补读比单纯提示模型更稳。

当前图片策略最多可保留“3 个窗口最新图＋3 张固定图＋最近召回图”。这不是严格的总计 3 张，也不是每窗口最多 3 张。是否过多应看主模型延迟，而不是凭图片张数决定。

JPEG q60 全尺寸可以保持，不必再争论格式。

怎么验证

选取需要前后对照、跨窗口抄写、用户中途改要求的任务，比较：

- 关键约束跨两次压缩后是否完整；
- token 误用、重复观察、证据图召回次数；
- 主模型首 token 延迟、缓存命中、总耗时；
- 最终成功率。

必须同时测成功率。上下文变短但遗忘更多，不算优化。

6. 离线与在线评测：新数字更清楚，但不能扩大解释

问题在哪

先更新结果口径。新版报告是：

- 185/361 = 51.25%：计划任务口径，infra 和缺失计失败。

建议怎么改

1. 同一任务及其布局变体必须同组；应用领域不等于任务模板。

另一个具体配置问题：role_enabled() 对 feasibility、verifier、judge、grounder 直接返回 true；配置了端点后，单角色 _ENABLE=0 不能关闭它们。roles.rs

建议怎么改

四层结构可以保留。Tauri 管可信 UI、生命周期和密钥；Pi 管模型循环；门管授权与派发；驱动管平台接口。把这些合进一个进程，不会自动减少主要模型延迟。

真正应收缩的是门里的 agent 功能：

- planner、search、compact 放客户端或暂时关闭；
- verifier 只验证明确后置条件；
- mandatory risk reviewer 保留独立；
- 配置优先级统一为“显式关闭高于任何组开关和端点存在”。

工具返回以结构化状态为准，尤其保证 partial、unknown、input_required、done_by_person 各自有稳定语义。建议补统一的执行状态、续接 ID、已完成批量索引和后置条件证据，不靠模型解析解释文字。

桌面打包方面，新版已经处理固定组件、环境白名单、无钥匙串时仅内存存储等问题。下一步重点是：

- Linux 明确 X11 支持范围，测试 AT-SPI/DBus 丢失后的行为；
- Windows 保持普通权限，UAC、锁屏、RDP 断开转真人；当前不提供 run_command 比套用 bash 规则合理；
- macOS 验证实际发布包的签名、权限授予与升级后权限保持；
- 清晰列出缓存、图片、日志、钥匙串和用户文档的卸载边界；
- 包内校验和解决完整性，发行来源真实性仍需要签名或可信发布链。

怎么验证

角色一次只消融一个因素，报告任务成功、总耗时、尾部耗时和角色改变了什么决策。打包测试必须使用安装后的产物，包括停止、崩溃、断连、升级、回滚与卸载；CI 构建成功不能代替 Windows/macOS 真机验证。
